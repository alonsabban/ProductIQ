🏗 General Architecture

ProductIQ is a Next.js SSR application hosted on AWS Amplify. Users authenticate through Amazon Cognito (restricted to @paloaltonetworks.com), then interact with a chat interface that routes questions to an AWS Bedrock Knowledge Base grounded in ~23,000 official Idira product documents.

⚡ Data Flow

A question travels from the user's browser through Amplify's SSR Lambda, hits the Bedrock RetrieveAndGenerate API which performs semantic vector search across the Idira document corpus, then returns a grounded answer with source citations — all in a single API round-trip.

Why RetrieveAndGenerate?

Rather than a raw LLM call, Bedrock's RetrieveAndGenerate API first embeds the user query with Titan Embed v2, performs cosine similarity search across the pre-indexed document vectors, retrieves the top-5 most relevant chunks from S3, then feeds them as context to Claude. This grounds every answer in the actual documentation — hallucinations about product features are minimized.

Multi-Turn Session Context

Bedrock tracks conversation history server-side via a sessionId. The frontend persists one sessionId per chat session. Follow-up questions ("How do I configure that?") automatically have the prior Q&A in context without re-sending history. New sessions get a fresh sessionId from Bedrock on the first response.

Credential Isolation

AWS credentials for Bedrock are stored as Amplify environment variables (at both app and branch level). They're injected into the SSR Lambda at runtime — never baked into the client bundle. A dedicated IAM user (productiq-bedrock) with a minimal policy — only RetrieveAndGenerate on KB CZIH7OWOAT.

Document Corpus

~23,140 HTM files mirrored from the official Idira/CyberArk product documentation. Stored in S3 bucket cyberark-kb-docs-mirror-821788677871. Pre-chunked and embedded by Bedrock into the Knowledge Base. No IP concern — all documents are publicly available CyberArk product docs.

🔄 User Flows

The four primary flows: first-time authentication, sending a chat message (happy path), managing multiple conversation sessions, and the unanswered question handling flow.

Flow 1 — First-Time Sign-In (Cognito PKCE OAuth)
1
User visits app URL
ChatShell mounts and runs checkAuth(). No session found → calls signInWithRedirect().
2
Amplify PKCE flow starts
Amplify v6 generates a PKCE code verifier, stores it in localStorage, then redirects the browser to the Cognito Hosted UI.
3
Email domain validation (new users)
On registration, the Pre Sign-Up Lambda fires. If the email doesn't end with @paloaltonetworks.com, registration is blocked before the account is created.
4
Auth code redirect
Cognito redirects back to /?code=…. Amplify exchanges the code for tokens using the stored PKCE verifier.
5
Session verified
ChatShell detects ?code= in URL and retries getCurrentUser() up to 10× (600ms apart) while Amplify finishes token exchange. Email is read from idToken.payload.email.
Flow 2 — Sending a Message (Happy Path)
Flow 3 — Session Management
1
Multiple independent sessions
Each session has its own messages[] array and its own bedrockSessionId. Bedrock maintains conversation context per session on the server side.
2
Auto-titling
When the user sends the first message in a session, the session title is automatically set to the first 40 characters of that message — displayed in the sidebar for easy navigation.
3
Safe deletion
Deleting the last remaining session automatically creates a fresh empty one so the UI is never in an empty state.
Flow 4 — Unanswered Question Handling

When Bedrock returns zero source citations, the question is flagged as unanswered and routed based on whether the product can be auto-detected.

Detection Logic
1
Zero-source signal
If Bedrock's sources.length === 0, the question is considered unanswered. This check lives in /app/api/chat/route.ts.
2
DynamoDB logging
The question, userId (Cognito email), sessionId, timestamp, and product are written to productiq-unanswered-questions in DynamoDB on-demand. Logging failures are silent so they never break the chat response.
3
Privacy
The userId (question author) is stored in DynamoDB for future PM routing but is never shown in the public /unanswered dashboard visible to all users.
Unanswered Questions Dashboard
1
Location
Accessible at /unanswered via the sidebar nav. Visible to all logged-in users.
2
Data source
Client-side fetch to GET /api/unanswered which does a full DynamoDB Scan, sorted newest-first in JS. Includes a refresh button.
3
Columns shown
Date & time · Product (or "Unknown") · Question text. User identity is intentionally omitted from the table.
